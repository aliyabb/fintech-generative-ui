# 生成式 UI：让模型返回界面，而不是段落

金融产品的核心体验问题是**看不懂成本**。而成本本身是结构化的——本金、期数、费率、时间。
用文字描述它，是把结构化的东西压成一维；用表格和对比条呈现，更接近事实的形态。

这个项目验证一件事：**让模型输出界面结构而不是文字，代价是什么，怎么把代价压下去。**

**在线演示 → [aliyabb.github.io/fintech-generative-ui](https://aliyabb.github.io/fintech-generative-ui/)**
**产品需求文档 → [PRD](docs/PRD_费率透明化界面.md)**　·　
**用户测试 → [方案](docs/用户测试方案.md) · [执行指南](docs/如何执行用户测试.md) · [测试页面](https://aliyabb.github.io/fintech-generative-ui/usertest.html)**

## 核心结果

| 指标 | v1 初版 | v2 序列契约 | v3 局部容错 |
|---|---|---|---|
| **结构有效率** | 58% | 75% | **92%** |
| **降级率**（回退纯文本）↓ | 42% | 25% | **8%** |
| 平均组件数 | 1.0 | 1.67 | 1.83 |
| 平均延迟 | 13.95s | 7.14s | 7.19s |

同一组 12 个问题 × 2 次重复 = 24 次生成，同一模型、同一温度，**只改契约与容错设计**。

三次修改各自解决一类失败：模型想输出组件序列而契约只允许单个；
让模型复述长表格导致输出截断；以及**一个组件有瑕疵就把整个响应丢掉**。

> 每个数字由 `src/build_site.py` 从 `results/reliability_v*.json` 读取。

## 模型输出什么

不是段落，是组件序列：

```json
[{"component":"fee_comparison",
  "data":{"title":"分期真实成本","advertised_label":"名义费率",
          "advertised_value":"7.2%","actual_label":"IRR口径真实年化",
          "actual_value":"13.03%","note":"手续费按本金全额计收，不随剩余本金递减"}},
 {"component":"risk_card","data":{...}}]
```

六种组件：`fee_comparison`（宣传费率 vs 真实年化对比条）、`repayment_schedule`（还款计划表）、
`product_compare`（客观参数对比）、`risk_card`（风险等级卡）、`clarify`（参数不足时追问）、
`text`（降级）。契约定义在 `src/schema.py`。

## 三次修改，各自值多少

同一组 12 个问题、同一模型、同一温度，只改契约设计——所以效果可归因。

### 修改一：从"单个组件"改为"组件序列"

初版要求模型输出**一个** JSON 对象，用贪婪正则 `{.*}` 提取。

实测发现模型倾向于**连续输出多个组件**——它想组合出一个多层界面：
对比条 + 风险卡 + 追问表单。贪婪正则把它们连成一段，解析失败。

这不是模型不听话，是**契约没有表达模型想做的事**。改为序列后，这类输出从失败变成合法结果。

### 修改二：模型定版式，代码填数据

初版让模型输出还款计划的逐期明细。12–24 行表格把输出撑到 `max_tokens` 截断，
JSON 不完整而降级——这是 v1 一半失败的来源。

改为：**模型只决定用什么组件、怎么组织；逐期数据由 `calc.py` 计算后注入。**
可靠性和正确性同时改善——模型本来也算不对这些数字。

这条分工后来被写进了[能力边界决策表](https://github.com/aliyabb/fintech-ai-boundary/blob/main/docs/AI能力边界决策表.md)第 5 条。
**这条边界是被失败教出来的，不是设计出来的。**

### 修改三：局部失败不等于整体失败

前两次修改之后仍有四分之一降级。打开失败样本，发现三种情况：
模型组合了 3 个组件、其中 1 个少一个字段；数组里某个对象写成了
`{"data":"content":...}` 这种残缺形式；整个数组少了一个右括号。

**共同点是：大部分内容其实是好的。**

初版一遇到任何问题就把整个响应扔掉、退回纯文本——
把 2 个正确的组件连同 1 个有瑕疵的一起丢了，对用户是更差的结果。
改为分层容错：整块解析失败就救内部的合法对象；单个组件字段不全就丢掉它、保留其余；
一个合法组件都没有，才降级为纯文本。

三个版本各自保留独立的解析器（`src/variants.py`），
任何人重跑 `bench.py v1/v2/v3` 都能复现出对应那一行的数字——
否则"改进了多少"这个结论就无法核验。

## 降级是产品的一部分

生成式 UI 的代价是结构可能无效。因此每次生成都过 schema 校验，失败一律降级为纯文本。

**宁可退回文字，不可渲染出错误界面。** 在金融场景里，一个字段错位的费率表
比一段模糊的文字危险得多——它看起来像是精确的。

## 可查找性：一个代码能测的替代指标

"用户是否更看得懂"必须由真人回答。但有一部分是**客观可测**的：
同样的信息、两种呈现形式，用户要读过多少内容才能碰到那个关键数字。

对同一组材料（内容完全一致，只有形式不同）测三件事——
关键数字是否出现、按阅读顺序它前面有多少字、总共多少字。
结果见 `results/findability.json`，由 `src/findability.py` 生成。

### 结果：更好扫描，但表达力更窄

生成式 UI 把关键数字放在**大约一半的位置、一半的篇幅**里——更容易扫到。
但命中率反而低于纯文字。这不是实现缺陷，是**结构化本身的代价**。

第一次测出来，UI 在"手续费一共多少钱"上完全没命中：
模型选了 `fee_comparison`，而这个组件当时只有费率、没有金额字段——
**答案根本不在界面上。**一个讲成本的组件不显示成本金额，是契约缺陷。
于是加了必需字段 `total_fee`，并**重跑了全部三个版本的基准**：
改了校验规则，之前公布的数字就不再对应现在的代码，必须重测而不是沿用。

修好之后，漏的变成了另一个问题：**"实际年化是宣传费率的几倍"**。
组件里有 7.2%、有 13.03%、现在也有 864 元，
但**没有 1.81 倍这个数**——它是从两个数推出来的，而组件只显示它有字段的东西。

这就是生成式 UI 的根本权衡：

> **文字能回答任何问题，组件只能回答它的 schema 预先想到的问题。**
> 换来的是：想到了的那些问题，答案离用户近一倍。

正确的产品结论不是"再加一个 `multiple` 字段"——那是拿三道测试题去过拟合契约。
正确的结论是：**覆盖预期问题集合，其余交给文字降级。**
系统本来就有降级通道，这个测量说明了它为什么必须一直存在。

## 用户测试

[测试页面](https://aliyabb.github.io/fintech-generative-ui/usertest.html)可以直接使用：
按被试编号自动分配条件顺序（组内对照 + 两组数字抵消记忆效应），
逐题计时、记录信心评分，结束后导出 JSON。全程浏览器本地运行，不上传数据。

把导出的 JSON 存进 `usertest_data/`，运行 `python3 src/analyze_usertest.py` 即可。
**没有数据时该脚本不产出任何指标**——不允许在未执行测试的情况下出现估计值。
完整流程见 [执行指南](docs/如何执行用户测试.md)。

### 结果：6 人跑完，但主要发现被自己的材料缺陷推翻

原始数据见 `usertest_data/`，汇总见 `results/user_test.json`。

| 任务 | 文字条件 | 生成式 UI | 结论 |
|---|---|---|---|
| 相差倍数、手续费总额、提前还款、实际年化 | 6/6 | 6/6 | 有效 |
| 风险等级 R4 | 0/6 | 4/6 | **无效，见下** |

#### 为什么风险等级那一题作废

试点中最显眼的现象是：文字条件下 6 人全都答不出"R4 意味着什么"。
看起来像是"散文容易把非数字信息一笔带过"。

**核对材料后发现不是这样。** 文字条件在这道题上给出的内容是一句拒答：

> 您咨询的"智选混合 C"不在本行信用卡账单分期业务范围内，**无法提供该理财产品的风险等级信息**。

答案根本不在材料里。被试答不出来，不是因为散文埋没了信息，而是因为**信息不存在**。

原因在材料生成脚本：文字条件的检索**每组只做一次**，
用一条关于分期的查询取回 5 个片段，再把同一份上下文喂给全部 5 道题。
风险等级问的是理财产品，这份上下文里没有对应片段，模型于是正确地拒答了。
而 UI 分支是**逐题检索**的，拿到了 `risk_card` 需要的片段。

**两个条件呈现的内容不一致——实验最核心的控制被破坏了。**
基于这道题的任何比较结论都不成立，包括我此前写下的
"结构化不允许信息被省略"。**该结论作废。**

#### 还剩下什么

- 四道数值题在两个条件下都是 6/6。**没有测出差异**，
  这本身是有效结果：对于"答案是一个数字"的问题，两种形式都够用。
- 试点验证了工具链可用：分配、计时、导出、判分、汇总全部跑通。
- **试点抓到了一个足以毁掉正式测试的设计缺陷。** 这正是试点存在的意义。

#### 已修与待做

- 已修：材料生成改为**两个条件逐题检索、使用同一条查询**（`src/make_test_materials.py`）
- 已归档：缺陷版材料保留为 `results/test_materials_v1_flawed.json`，与这 6 份数据对应
- 待做：用修正后的材料**重新招募**被试。已跑过的 6 人不能复用——他们见过旧材料

PRD 里理解度三行仍然是"未测量"，现在有了更具体的理由：
**测过一轮，测错了，知道错在哪，也知道怎么重测。**

## 运行

```bash
# 复现演示页（无需模型，回放已提交的录制结果）
python3 src/build_site.py

# 实时演示（需 LM Studio 加载 qwen/qwen3.5-9b 并启动本地服务）
python3 src/serve.py          # → http://127.0.0.1:8000

# 重跑可靠性基准（三个版本各 24 次生成）
python3 src/bench.py v1 && python3 src/bench.py v2 && python3 src/bench.py v3
```

## 数据从哪来

演示页里的每个界面都是**真实模型输出的录制回放**，不是手写示例。

```
results/schemas_v{1,2,3}.json        每次生成的完整结构与元数据
results/reliability_v{1,2,3}.json   可靠性指标
results/findability.json            可查找性客观指标
results/user_test.json              用户测试结果（尚未产生）
        ↓ src/build_site.py
docs/index.html + docs/data.json              演示页
```

## 已知局限

- 12 个问题 × 2 次重复的样本量偏小，绝对数值有波动
- 只测了一个模型，未验证契约设计在其他模型上的迁移性
- 渲染器只认识 6 种组件；新增组件需要同时改 `schema.py` 与 `render.js`，这是生成式 UI 的固有成本
- 用户理解度尚未有效测量：试点跑完 6 人但因材料生成缺陷作废（见「用户测试」一节），需用修正后的材料重测
- 可查找性只是替代指标，不能等同于理解度
