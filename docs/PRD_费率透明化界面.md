| | |
|---|---|
| 状态 | 原型已完成；用户测试处于小样本试点阶段，正式测试待执行 |
| 负责人 | 产品 |
| 关联 | [评测台](https://github.com/aliyabb/fintech-qa-compliance-eval) · [能力边界决策表](https://github.com/aliyabb/fintech-ai-boundary) |

## 1. 背景

分期入口当前展示「每期手续费 0.6%」。12 期加起来 7.2%，用户据此判断成本。

但手续费按**本金全额**计收，而本金逐期减少——IRR 口径的真实年化是 **13.03%**。
3 期更极端：名义 1.65%，真实 9.87%，**相差 5.98 倍**。

这不是营销话术问题，是**信息结构问题**：成本本身由本金、期数、费率、时间四个维度构成，
却被压缩成一句话。用户不是不看，是看了也还原不出来。

监管口径（F030）要求以年化形式明示且采用 IRR 口径。但「明示了」和「用户理解了」是两回事——
把 13.03% 印在页面角落同样算明示，却不解决任何问题。

## 2. 目标与非目标

**目标**
- 用户在做分期决策前，能正确回答「这笔钱实际成本是多少」
- 满足 F030 的 IRR 明示要求，且是有效明示而非形式明示

**非目标**
- 不承担提升分期转化率的目标。透明化预期会**降低**转化（见[商业论证](https://github.com/aliyabb/fintech-ai-boundary/blob/main/docs/商业论证_盈亏平衡.md)），这是已知代价
- 不做产品推荐或额度建议——属能力边界决策表 D 档，无投顾资质
- 不改变分期产品本身的定价

## 3. 用户故事

> 作为一个**正在考虑把 12,000 元账单分期的持卡人**，
> 我希望**一眼看出这笔分期实际要多花多少钱、跟宣传的费率差多少**，
> 以便**在按下确认前知道自己在承担什么**。

关键场景三个：
1. **成本确认** —— 「分 12 期到底多花多少钱」→ 对比条 + 还款计划表
2. **方案比较** —— 「3 期和 12 期哪个更划算」→ 客观参数对比表（不含推荐结论）
3. **参数不足** —— 「我想分期，成本高吗」→ 追问表单，而不是猜一个数字回答

## 4. 方案

**核心决策：让模型返回界面结构，而不是一段文字。**

成本是结构化的，就该用结构呈现。模型输出组件序列，前端渲染：

| 组件 | 用途 |
|---|---|
| `fee_comparison` | 宣传费率 vs IRR 真实年化，对比条 |
| `repayment_schedule` | 逐期还款计划表 |
| `product_compare` | 客观参数对比（含不构成投资建议的声明） |
| `risk_card` | 风险等级说明 |
| `clarify` | 参数不足时追问 |
| `text` | 降级兜底 |

**分工原则：模型决定用什么组件、怎么组织；数字由确定性模块计算后填充。**

这条来自能力边界决策表第 4、5 条：金额与年化计算属 B 档（确定性代码）。
依据是评测台的实测——方案 B 检索命中率 90%，计算类准确率仍只有 50%。
**找到正确条款不能解决算术。**

## 5. 成功指标

| 层级 | 指标 | 目标 | 当前状态 |
|---|---|---|---|
| 可靠性 | 结构有效率 | ≥ 95% | **92%**（24 次生成）**未达标** |
| 可靠性 | 降级率 | ≤ 5% | **8%** **未达标** |
| 理解度 | 真实年化回答正确率（UI vs 文字） | 相对提升 ≥ 30% | **未测量** |
| 理解度 | 完成任务耗时 | 不劣于文字 | **未测量** |
| 体验 | 信息过载主观评分 | 不上升 | **未测量** |
| 护栏 | 分期申请转化率 | 降幅 < 15% | 需线上实验 |
| 护栏 | 30 日投诉率 | 不上升 | 需线上实验 |

理解度三项由 [用户测试方案](用户测试方案.md) 覆盖。**试点已完成 6 人，但结论作废**：
文字条件在风险等级一题上因材料生成缺陷未包含答案，两个条件内容不一致，
实验的核心控制被破坏。详见 README「用户测试」一节。

有效的部分：四道数值题在两个条件下均为 6/6，**未测出差异**——
对于答案是一个数字的问题，两种形式都够用。

缺陷已修（材料生成改为两条件逐题检索、同一查询），
缺陷版材料归档于 `results/test_materials_v1_flawed.json`。
**这三行仍保持"未测量"**，需用修正后的材料重新招募被试。

## 6. 技术约束

- 6 种组件，新增组件需同时改 `src/schema.py` 与 `docs/render.js`——这是生成式 UI 的固有成本
- 结构校验失败一律降级为纯文本。**宁可退回文字，不可渲染出错误界面**：
  金融场景下一个字段错位的费率表比一段模糊文字危险得多，因为它看起来是精确的
- 局部失败不等于整体失败：3 个组件里 1 个有瑕疵时保留其余 2 个
- 模型本地部署（数据不出域），平均延迟约 11 秒——**此延迟不可接受于生产环境**，
  需要流式渲染或预生成，见第 8 节

## 7. 实验设计

**第一阶段（离线，已完成）**：契约可靠性。同一组问题、同一模型、同一温度，
仅改契约设计，三版对比：降级率 42% → 25% → 8%。

**注意：曾达到过 0%，但那是在 `fee_comparison` 加入必需字段 `total_fee` 之前。**
加字段收紧了校验，也修好了'问手续费总额时答案不在界面上'的缺陷——
可靠性因此从 0% 降级回升到 8%。**这是有意的取舍**：
宁可多降级几次，也不要渲染出一个讲成本却不显示金额的界面。
当前数字始终以 `results/reliability_v3.json` 为准。

**第二阶段（有人参与，未执行）**：理解度。6–8 名被试、组内对照、5 个任务、
正确答案来自计算模块。样本量不足以做统计推断，只能发现明显差异和可用性问题——
方案里已写明这一点，也预先写好了各种失败情形对应的下一步。

**第三阶段（线上，未开始）**：转化影响。见[实验设计文档](https://github.com/aliyabb/fintech-ai-boundary/blob/main/docs/实验设计_真实年化展示.md)，
含决策规则与样本量计算。

## 8. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| 生成延迟约 11 秒 | 生产不可用 | 高频问法预生成 + 流式渲染；本项目未实现 |
| 契约与渲染器需同步演进 | 迭代成本 | 组件数量克制，新增需明确收益 |
| 单模型验证 | 迁移性未知 | 未测其他模型，属已知缺口 |
| 组件过多造成信息过载 | 体验反向 | 用户测试的反向指标覆盖；默认折叠明细 |
| 透明化降低转化 | 商业指标承压 | 已量化为已知代价，按合规口径立项 |
