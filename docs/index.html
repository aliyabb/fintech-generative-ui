生成式 UI：让模型返回界面，而不是段落

金融产品的核心体验问题是"看不懂成本"。而成本本身是结构化的—— 费率、期数、金额、时间。用表格和对比条呈现，比用文字描述更接近事实的形态。

修改一：从"单个组件"改为"组件序列"

初版要求模型输出一个 JSON 对象。实测模型倾向于连续输出多个组件—— 它想组合出一个多层界面（对比条 + 风险卡 + 追问表单）。 初版用贪婪正则 {.*} 提取，把多个对象连成一段而解析失败。 这不是模型不听话，是契约没有表达模型想做的事。改为序列后，这类输出从失败变成合法结果。

修改三：局部失败不等于整体失败

v2 仍有 25% 降级。打开失败样本发现三种情况： 模型组合了 3 个组件、其中 1 个缺一个字段；数组里某个对象写成了 {"data":"content":...} 这种残缺形式；整个数组少了一个右括号。 共同点是：大部分内容其实是好的。

初版一遇到任何问题就把整个响应丢掉、退回纯文本—— 把 2 个正确的组件连同 1 个有瑕疵的一起扔了，对用户是更差的结果。 v3 改为分层容错：整块解析失败就救内部的合法对象， 单个组件字段不全就丢掉它保留其余，一个合法组件都没有才降级。

修改二：模型定版式，代码填数据

初版让模型输出还款计划的逐期明细。12~24 行表格把输出撑到 max_tokens 截断， JSON 不完整而降级。改为：模型只输出组件类型与表头，逐期数据由 calc.py 计算后注入。 可靠性和正确性同时改善——模型本来也算不对这些数字。

这条分工后来被写进了能力边界决策表第 5 条： 这条边界是被失败教出来的，不是设计出来的。

可靠性：降级是产品的一部分

生成式 UI 的代价是结构可能无效。因此每次生成都过 schema 校验， 校验失败一律降级为纯文本。宁可退回文字，不可渲染出错误界面—— 在金融场景里，一个字段错位的费率表比一段文字危险得多。

可查找性：一个代码能测的客观指标

"用户是否更看得懂"必须由真人回答。但有一部分是客观可测的： 同样的信息、两种呈现形式，用户要读过多少内容才能碰到那个关键数字。 对内容完全一致、只有形式不同的同一组材料，测关键数字是否出现、 按阅读顺序它前面有多少字、总共多少字。

更好扫描，但表达力更窄。 生成式 UI 把关键数字放在大约一半的位置、一半的篇幅里，更容易扫到； 但命中率反而低于纯文字。这不是实现缺陷，是结构化本身的代价。

第一次测出来，UI 在"手续费一共多少钱"上完全没命中：模型选了 fee_comparison， 而该组件当时只有费率、没有金额字段——答案根本不在界面上。 加了必需字段 total_fee 后重跑了全部三个版本（改了校验规则， 旧数字就不再对应现在的代码，必须重测而不是沿用）。

修好之后漏的变成了另一个问题："实际年化是宣传费率的几倍"。 组件里有 7.2%、有 13.03%、也有 864 元，但没有 1.81 倍—— 它是从两个数推出来的，而组件只显示它有字段的东西。
这是生成式 UI 的根本权衡： 文字能回答任何问题，组件只能回答它的 schema 预先想到的问题； 换来的是——想到了的那些问题，答案离用户近一倍。

正确的产品结论不是"再加一个 multiple 字段"， 那是拿三道测试题去过拟合契约。正确的结论是： 覆盖预期问题集合，其余交给文字降级。 系统本来就有降级通道，这个测量说明了它为什么必须一直存在。

这不是理解度的替代品，只是把"信息埋得多深"量化出来。 真正的理解度仍然标注为未测量。

用户测试

6 人跑完了试点， 而试点最主要的发现被我自己的材料缺陷推翻了。

任务文字条件 生成式 UI结论
相差倍数、手续费总额、提前还款、实际年化6/66/6有效
风险等级 R40/64/6无效
为什么风险等级那一题作废。 试点里最显眼的现象是文字条件下 6 人全都答不出"R4 意味着什么"， 看起来像是"散文容易把非数字信息一笔带过"。

核对材料后发现不是这样——文字条件在这道题上给出的是一句拒答： 「您咨询的"智选混合 C"不在本行信用卡账单分期业务范围内，无法提供该理财产品的风险等级信息」。 答案根本不在材料里。

原因在材料生成脚本：文字条件的检索每组只做一次，用一条关于分期的查询取回片段， 再把同一份上下文喂给全部 5 道题；风险等级问的是理财产品，上下文里没有对应片段， 模型于是正确地拒答了。而 UI 分支是逐题检索的，拿到了 risk_card 需要的片段。

两个条件呈现的内容不一致——实验最核心的控制被破坏了。 基于这道题的任何比较结论都不成立，包括我此前写下的"结构化不允许信息被省略"。 该结论作废。
还剩下什么。 四道数值题在两个条件下都是 6/6——没有测出差异， 这本身是有效结果：答案是一个数字时，两种形式都够用。
试点还验证了工具链可用，并且抓到了一个足以毁掉正式测试的设计缺陷。 这正是试点存在的意义。
